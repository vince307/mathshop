# Contract Surfaces

Registry of load-bearing names — tables, columns, policies, shared functions, and the paths that depend on them. When a change renames or reshapes a surface listed here, treat it as **breaking** and provide a migration story for every consumer.

Each H2 below is a surface name. New account-owned tables must add an entry here as part of their migration (see [`rls-isolation.md`](./rls-isolation.md)).

> Convention established by Foundation F-01 (`per-account-isolation-contract`).

## public.child_profiles

The first account-owned table. Child play-profiles owned by a parent account. Carries consciously-collected child PII (`name`, `age` — a deliberate S-01b override of the PRD no-PII guardrail), RLS-isolated per account; see the Columns note below.

- **Defined in:** `supabase/migrations/20260609120000_child_profiles_isolation.sql`; identity columns added in `supabase/migrations/20260628120000_child_profiles_add_identity.sql` (S-01b); gameplay-state columns added in `supabase/migrations/20260630120000_child_profiles_add_gameplay_state.sql` (S-04); `coins` renamed to `wallet_balance` in `supabase/migrations/20260701120000_rename_coins_to_wallet_balance.sql` (S-05); `skill_state` jsonb added in `supabase/migrations/20260701140000_child_profiles_add_skill_state.sql` (S-07); `difficulty_state` jsonb added in `supabase/migrations/20260825130000_child_profiles_add_difficulty_state.sql` (adaptive-task-engine P3).
- **Owner column:** `account_id uuid not null references auth.users(id) on delete cascade` — RLS predicate `auth.uid() = account_id`.
- **Columns:** `id`, `account_id`, `avatar`, `theme`, `name`, `age`, `starting_level`, `wallet_balance`, `completed_shift_count`, `business_level`, `shop_state`, `skill_state`, `difficulty_state`, `created_at`, `updated_at`. `name` + `age` are **consciously-collected child PII** (S-01b override of the PRD no-PII guardrail) — RLS-isolated by the policies below, app-validated/escaped, never logged; `age` is check-constrained `6–9`. Gameplay state (S-04/S-05): `wallet_balance` (the spendable wallet/Portfel, renamed from `coins` in S-05; check `>= 0`)/`completed_shift_count` (check `>= 0`), `business_level` (check `>= 1`, **mutable progression — distinct from the frozen `starting_level` difficulty band**), `shop_state` jsonb (reserved for S-05) — `{ purchased: string[] }`, plus an optional `purchasedMeta` (`{ [upgradeId]: { world, at } }`, F5): **write-only in v1**, written by `buyUpgrade`, read by nothing and safely ignorable by every reader (`readPurchased` is untouched). It exists because `/app/worlds` makes `theme` mutable, so a purchase recorded without a world could never afterwards be attributed to one. `skill_state` jsonb (S-07): per-competency progress `{ math|money|decisions: { firstTryCorrect, completed, misses } }`, monotonic, normalized by `readSkillState` (`src/data/skills.ts`). `difficulty_state` jsonb (adaptive-task-engine P3): the continuous per-competency difficulty `{ math|money: number }` on the `[0,1]` scale defined by `src/data/adaptive.ts`, where `0` / `0.5` / `1` reproduce the legacy tier-1/2/3 generator parameters **exactly** (that calibration is what let P3 ship without the child seeing a change); normalized by `readDifficultyState`, which — unlike `readSkillState` — takes `starting_level`, because a missing/garbage value falls back to the age-derived seed and everything is clamped into `[0, ceilingForLevel(starting_level)]`. Deliberately **not** inside `skill_state`: that column is monotonic and gates upgrades, `d` is neither, and `readSkillState` rebuilds its rows from a fixed three-field shape so a `difficulty` key placed there would be silently dropped on the next write. Pre-P3 rows are `{}` and normalize on read, so there was no backfill and no data migration — history in `skill_state` is deliberately ignored, so no existing child jumped difficulty on the day it shipped. **Never written from client input (P5):** `recordShiftResult` recomputes the value by folding the reported per-task OUTCOMES (`task_attempt.first_try`) through `foldShiftOutcomes` from the stored state, bounded by `ceilingForLevel(starting_level)` — the same pure rule the island ran while the shift was played. The `attempts[].difficulty` field the client sends is telemetry (what a task was generated at) and is stored verbatim in `task_attempt`, but is never read back into this column; the plan's `ceiling` that crosses the wire is a bound for the island, never the bound this write is checked against. So a tampered client can only misreport how well its own child did, which moves its own difficulty inside its own age band. All covered by the existing four policies (column-agnostic); written server-side via `recordShiftResult` / `buyUpgrade` / `POST /api/shifts/complete`. `theme` is **no longer write-once** (F5): it is mutated server-side via `updateChildProfileTheme` — see the world-change surface below.
- **RLS:** enabled; four per-operation policies, all `to authenticated`:
  - `child_profiles_select_own` — `for select using (auth.uid() = account_id)`
  - `child_profiles_insert_own` — `for insert with check (auth.uid() = account_id)`
  - `child_profiles_update_own` — `for update using (...) with check (...)`
  - `child_profiles_delete_own` — `for delete using (auth.uid() = account_id)`
- **`updated_at` trigger:** `child_profiles_set_updated_at` (`before update`, reuses `set_updated_at()`).
- **Isolation test:** `tests/child-profiles-isolation.test.ts` (run by CI as a merge gate).
- **Deletion surface (MAT-17):** see the [Child-profile deletion](#child-profile-deletion-rls-surface) surface below (`POST /api/profiles/delete` → `deleteChildProfile` via `child_profiles_delete_own`; `shift_log` cascades).
- **World-change surface (F5):** `POST /api/profiles/world` → `updateChildProfileTheme` via `child_profiles_update_own`; the closed slug set is enforced in zod at the route (`WORLD_SLUGS`), there is **no DB CHECK** on `theme`. Ownership is proven twice (the `resolveActiveProfile` read gate and the UPDATE policy itself) and never from client input. Isolation test: `tests/profiles-world.test.ts`.

## public.shift_log

Per-profile, per-shift history log (S-07) backing the parent weekly report (FR-016). One row per completed shift, plus one per upgrade purchase. Written server-side (`recordShiftResult` / `buyUpgrade`), `account_id` taken from the RLS-verified profile row (never client input, L-002).

- **Defined in:** `supabase/migrations/20260701150000_create_shift_log.sql` (S-07); `earned` added by `supabase/migrations/20260822120000_shift_log_add_earned.sql` (F4).
- **Owner column:** `account_id uuid not null references auth.users(id) on delete cascade` — RLS predicate `auth.uid() = account_id`.
- **Columns:** `id`, `account_id`, `profile_id` (`references child_profiles(id) on delete cascade`), `created_at`, `skills` jsonb (the per-competency delta this event exercised), `upgrade_purchased` text null (set only on a purchase event), `earned` integer null (F4 — the server-computed payout for a shift; **null means unknown**: a purchase event, or a pre-migration row, since there was no backfill. `sum(earned)` is therefore a lower bound, because `appendShiftLog` is best-effort and swallows its insert error). No `updated_at` (append-mostly; rows aren't mutated in normal flow).
- **Indexes:** `shift_log_account_id_idx` (`account_id`), `shift_log_profile_created_idx` (`profile_id, created_at` — the weekly-report query path).
- **RLS:** enabled; four per-operation policies, all `to authenticated`:
  - `shift_log_select_own` — `for select using (auth.uid() = account_id)`
  - `shift_log_insert_own` — `for insert with check (auth.uid() = account_id)`
  - `shift_log_update_own` — `for update using (...) with check (...)`
  - `shift_log_delete_own` — `for delete using (auth.uid() = account_id)`
- **Consumed by:** `src/lib/services/reports.ts` (`getWeeklyReport` / `aggregateWeeklyReport`, `listRecentActivity` — the child dashboard activity feed), `src/lib/services/child-profiles.ts` (writers), `e2e/helpers/accounts.ts` (`seedShiftWeek` — the first **test-side** writer, and the only writer anywhere that sets `created_at` explicitly: it pins each row at `12:00Z` on a `weekDayKeys` civil date so a bar cannot drift across the Europe/Warsaw day boundary or a DST weekend, and it sets `earned` explicitly because a `null` there flips `earningsKnown` to `false` and silently suppresses the parent's earnings tile).
- **Isolation test:** `tests/shift-log-isolation.test.ts` (table-level RLS), `tests/report-isolation.test.ts` (S-09 — the weekly-report read path itself: `getWeeklyReport` + profile listing, two signed-in accounts), `tests/recent-activity-isolation.test.ts` (F2 — **intra-account**: RLS here is account-scoped, so `listRecentActivity`'s app-side `.eq("profile_id", …)` is the only thing separating two children of the same parent; two profiles on one account, one row each).

## public.task_attempt

Per-task telemetry (adaptive-task-engine P1) backing the adaptive difficulty engine. Where `shift_log` records one aggregate row per completed shift, this records **one row per task**: which scenario ran, at what parameters, whether it was answered first try, how many misses it took, and how long it lasted. Written server-side, batched at shift end in the same call as `recordShiftResult`, `account_id` taken from the RLS-verified profile row (never client input, L-002). S-07 listed "no per-task-attempt history rows" as an explicit non-goal; this table lifts that.

- **Defined in:** `supabase/migrations/20260825120000_create_task_attempt.sql` (adaptive-task-engine P1).
- **Owner column:** `account_id uuid not null references auth.users(id) on delete cascade` — RLS predicate `auth.uid() = account_id`.
- **Columns:** `id`, `account_id`, `profile_id` (`references child_profiles(id) on delete cascade`), `created_at`, `shift_index` integer (0-based **positional** index within its shift, check `>= 0` — the adaptation guards are positional, so warm-up and closing-task behaviour are only analysable against it), `task_type` text (`counting` | `change_making`), `scenario` text (`count_till` | `give_change` | `stock_and_change` — free text, **no DB CHECK**), `competency` text (`math` | `money`), `difficulty` real null (the continuous `d` the task was generated at, from `src/data/adaptive.ts`; check `0..1` when present. **Null means not measured, not zero** — zero is a real difficulty. Only P1/P2 rows carry null: they predate the continuous scale, and writing a normalised tier there would have put two incomparable quantities in one column of the table whose whole purpose is tuning. Telemetry only — from P5 the persisted difficulty is recomputed server-side from the reported outcomes, never taken from this field), `params` jsonb (the generated numbers — `{ targetCount }` for counting, `{ paid, price, change, availableCount, stockCount? }` for change-making), `first_try` boolean, `misses` integer (check `>= 0`), `duration_ms` integer null (time on task, measured to the moment the answer was accepted — it **excludes** the fixed 1400 ms celebration beat in `useCoinTask`). No `updated_at` (append-only; rows are never mutated).
- **Indexes:** `task_attempt_account_id_idx` (`account_id`), `task_attempt_profile_created_idx` (`profile_id, created_at` — the analysis query path).
- **RLS:** enabled; four per-operation policies, all `to authenticated`:
  - `task_attempt_select_own` — `for select using (auth.uid() = account_id)`
  - `task_attempt_insert_own` — `for insert with check (auth.uid() = account_id)`
  - `task_attempt_update_own` — `for update using (...) with check (...)`
  - `task_attempt_delete_own` — `for delete using (auth.uid() = account_id)`
- **Deliberately no `shift_log_id` FK:** `appendShiftLog` (`src/lib/services/child-profiles.ts`) returns void and swallows its insert error by design; depending on the log row's id would force that best-effort contract to become mandatory and add an ordering dependency. Attempts correlate to their shift by (`profile_id`, `created_at`) plus `shift_index`.
- **Consumed by:** written by `recordShiftResult` (`src/lib/services/child-profiles.ts`, batched at shift end) via `POST /api/shifts/complete`, which validates the array against `src/data/attempts.ts` — the shared shape both sides build and check, so a column and its payload field cannot silently drift. No reader yet: the analysis path is what the table exists for, and the difficulty recompute lands in P5.
- **Isolation test:** `tests/task-attempt-isolation.test.ts` (run by CI as a merge gate).

- **Env dependency:** `PARENT_SESSION_SECRET` (astro.config.mjs `env.schema`) — HMAC key for the signed `parent_verified` session marker. Set on Vercel Production scope (added 2026-07-11 with MAT-17; Preview fails closed — no marker minting, so the report + deletion actions are unreachable there).

## Parent PIN routes (RLS surface)

The two write/read paths over `public.account_settings.pin_hash` (S-07 / FR-016). Both take the PIN from a `multipart/form-data` body and the account from the session — no account id is ever accepted from the client (L-002). `verifyPin` (`src/lib/services/parent-pin.ts`) is the **only** exported reader of `pin_hash`; neither route compares a hash itself.

- **`POST /api/parent/pin/verify`** (`src/pages/api/parent/pin/verify.ts`). Gate order: 503 (no RLS client) → 401 (no session user) → 400 (zod) → `verifyPin` under the atomic `register_pin_failure` throttle → mint the signed `parent_verified` marker → 200.
- **`POST /api/parent/pin/set`** (`src/pages/api/parent/pin/set.ts`) — set **or** change. Gate order: 503 (no RLS client) → 401 (no session user) → 503 (`pinExists` could not tell) → **403** (existing PIN and no valid `parent_verified` marker) → 400 (zod) → **the change gate** → `setPin` → re-mint the marker → 200.
  - **First set vs change.** With no `account_settings` row the route is **open** to any authenticated session (this is real onboarding — `parent-pin.astro` renders `set` mode there). With a row present it is a **change**, which requires the marker **and** `currentPin` re-proved through `verifyPin` — a possibly-15-minute-old marker alone is not enough, matching the bar `POST /api/account/delete` sets (see below). `hasPin` fails open by contract, so the route uses the fail-closed `pinExists` instead.
  - **The change gate is one `if (isChange)` block**, in this order: (1) `currentPin` present, else 400 `invalid` — an early `return`, never a skipped verification; (2) `verifyPin`; (3) `currentPin === pin` → 400 `same-as-current`, deliberately *after* (2) so the cheap comparison cannot be a pre-flight that skips burning a throttle attempt. Do not split it into separate `isChange` tests and never gate (2) on `currentPin` being truthy — that shape is a full bypass. `setPin` unconditionally clears `failed_attempts`/`locked_until`, so any path reaching it while locked would be a free lockout reset; keeping `verifyPin` ahead of it is what prevents that.
- **`STATUS_FOR` vocabulary** (duplicated verbatim in `verify.ts`, `set.ts` and `account/delete.ts` so islands share one copy map): `locked` → 429, `wrong` → 401, `no-pin` → 400, `error` → 500. A 401 means "wrong PIN" **only** when the body carries `reason: "wrong"`.
- **Tests:** `tests/parent-pin-routes.test.ts` (both gate orders, the change contract, throttle participation and the live-lock rejection of a correct PIN), `tests/parent-pin.test.ts` (service layer), `tests/account-settings-isolation.test.ts` (table RLS).
- **Known limitation K1 — the attempt counter never decays, so the lock expires but the budget does not.** `register_pin_failure` (`supabase/migrations/20260702120000_pin_failure_throttle_rpc.sql`) only ever `set failed_attempts = failed_attempts + 1`; nothing anywhere decrements it or ages it out. The only two resets are a **correct PIN** and **`setPin`**, both in `src/lib/services/parent-pin.ts`. `LOCKOUT_MS` is 60 000, so once the threshold is reached the **lock** clears after a minute while the **counter** stays at or above it — the next single wrong PIN re-locks immediately, and every wrong PIN after that re-locks again. Waiting out a lock therefore buys one attempt, not a fresh budget. This is intentional (it makes a slow brute-force strictly worse than a fast one) and is recorded here because nothing in the code says it. See the change gate above for why `setPin`'s unconditional reset must stay behind `verifyPin`.

## Account deletion (service-role surface)

Whole-account erasure (MAT-17) — the project's **first and only production service-role surface**. The GDPR right-to-erasure path: deleting the parent's `auth.users` row cascades every owned table (see the three surfaces above, all `on delete cascade`) plus `auth.sessions`.

- **Route:** `POST /api/account/delete` (`src/pages/api/account/delete.ts`). Gate order (all-or-nothing, each a hard stop): 503 (no RLS or admin client) → 401 (no session user) → 403 (invalid `parent_verified` marker) → 400 (zod) → PIN re-check via `verifyPin` (429 locked / 401 wrong / 400 no-pin — the atomic `register_pin_failure` throttle applies) → 400 (typed e-mail ≠ session e-mail) → `admin.auth.admin.deleteUser(user.id)` → best-effort `signOut()` + `clearAuthCookies` + delete `active_profile`/`parent_verified` → 200. The deletion target is **always** `user.id` from the session (`getUser()`), never client input (L-002).
- **Admin client:** `createAdminClient()` (`src/lib/supabase-admin.ts`) — plain `@supabase/supabase-js` client with the **service-role** key, `{ autoRefreshToken: false, persistSession: false }`, no cookie adapter. Used for **exactly one operation** (`deleteUser`); never to read/write app tables (that bypasses RLS, the project's highest-risk invariant). Fails closed: missing key → `null` → route 503.
- **Env dependency:** `SUPABASE_SERVICE_ROLE_KEY` (astro.config.mjs `env.schema`, `optional`). The most sensitive value in the project — Vercel **Production scope ONLY** (never Preview/Development; `infrastructure.md`), never the browser. `astro:env/server` import fails in client bundles, so islands cannot import the factory.
- **Tests:** `tests/account-deletion.test.ts` (full-cascade erasure across all three tables + auth user via admin read-back; wrong-PIN throttle; missing marker; e-mail mismatch; bystander isolation; absent-key 503).

## Auth cookie lifetime (session-policy surface)

How long a signed-in parent stays signed in. The parent chooses it once, at sign-in, via the "Zapamiętaj mnie" checkbox; everything below is what makes that choice stick. Registered as a surface because **every failure mode here is silent** — a wrong lifetime logs nobody out and crashes nothing, it just quietly restores a 400-day session or quietly drops one.

- **The only seam is `setAll` inside `createClient`** (`src/lib/supabase.ts`). It sets `maxAge` explicitly, **after** the two existing spreads, and *last-spread-wins* is the entire reason it works. Reordering those spreads — or "tidying" the explicit `maxAge` away — silently restores `@supabase/ssr`'s unchosen 400-day default (`DEFAULT_COOKIE_OPTIONS.maxAge`). Nothing fails.
- **`maxAge: undefined` is the mechanism, not an omission.** A spread cannot delete a key and the library's 400-day value is already in `options`, so "just don't set `maxAge`" is a no-op. `AstroCookies.set` does `Object.assign(serializeOptions, options)` and `cookie`'s `serialize()` guards on `if (cookie.maxAge !== undefined)` — an explicit `undefined` is what *removes* the attribute.
- **`createServerClient`'s `cookieOptions` is NOT a seam** — do not reach for it. Both write paths in `@supabase/ssr` 0.10.3 build `setCookieOptions` as `{ ...DEFAULT_COOKIE_OPTIONS, ...cookieOptions, maxAge: DEFAULT_COOKIE_OPTIONS.maxAge }`, re-asserting the library's own `maxAge` *after* the caller's. Anything passed there is silently discarded. (Anchor on the identifier `setCookieOptions`; it occurs twice.)
- **The removal guard is load-bearing.** Removals (sign-out, chunk cleanup) travel through this same `setAll` as `value: ""` + `maxAge: 0`, built by the library's `removeCookieOptions`. Without `setAll`'s `isRemoval` check, an unguarded lifetime override turns **sign-out** into an empty-valued *session* cookie the browser keeps, instead of an expired one. Only `tests/remember-me-cookie.test.ts` test 7 catches this: `tests/auth-session-gating.test.ts` stays green through it, because the test jar's `toCookieHeader()` filters empty values, so a replayed request looks signed out either way. Verified by running the break.
- **`maxAge` must NEVER be added to `AUTH_COOKIE_OPTIONS`.** `clearAuthCookies` spreads that object *after* its own `maxAge: 0`, via a direct `cookies.set` that bypasses `setAll` entirely — a lifetime living in there would override the deliberate expiry and break the env-missing sign-out path too.
- **The `remember_me` marker** (`src/lib/services/remember-me.ts`) persists the choice, because `setAll` re-writes the auth cookie on **every token refresh** (~hourly): a choice held only in the sign-in request is silently reverted an hour later, and no sign-in-only test can see it. Read it with `cookies.get()`, never from the `Cookie:` header — `getAll` reads only `requestHeaders`, where the marker does not exist yet on the request that sets it.
- **This marker is deliberately UNSIGNED**, unlike `RESET_MARKER_COOKIE` (`password-reset.ts`) and `PARENT_VERIFIED_COOKIE` (`parent-pin.ts`). Those are HMAC-signed because forging them *grants a privilege* — setting a new password, skipping the PIN gate. Forging this one lengthens only the attacker's own cookie in their own browser. Do not "harden" it by analogy.
- **Ordering in `POST /api/auth/signin`:** the marker is written *after* the `!supabase` guard and *before* `signInWithPassword`, because that call is what triggers `setAll`. Written afterwards, the first sign-in gets the wrong lifetime and then self-heals on the next refresh. The write is **unconditional** — ticked sets, unticked deletes; without the delete branch a stale marker re-lengthens every later sign-in forever.
- **Reach beyond sign-in — decided, not merely accepted (RF-1, 2026-08-26).** `setAll` is *every* auth-cookie write path, and only `POST /api/auth/signin` carries a checkbox. `GET /api/auth/confirm` (`verifyOtp` — email verification *and* password recovery) and `POST /api/auth/update-password` therefore mint their session with whatever marker the browser **already** carries: 30 days if the parent ticked the box on this device at an earlier sign-in, **browser-session** otherwise. Note what this is not: not a sign-out — the parent stays signed in, the session just does not survive closing the browser. That is the intended policy. 30 days is something a parent opts into on a device they consider theirs; clicking a link in an email is not that act, on a product whose parent surface is PIN-gated precisely because the device may be shared with the family. The reversal, if a maintainer ever wants it, is one call to `setRememberChoice(cookies, true)` in the route concerned — **not** a special case inside `setAll`, which cannot tell which route it is serving. Tests 8–11 pin both directions, so that edit turns 8 and 10 red: re-decide the policy, do not edit the tests.
- **`POST /api/auth/signup` writes no auth cookie at all in production**, so it is outside the surface above despite appearing to belong to it. With `enable_confirmations = true` (prod) `signUp` returns `session: null`; it mints a session only on a local stack, where `supabase/config.toml` has confirmations off. Deliberately untested for that reason — an assertion there would pin a config toggle and would break the moment someone flips confirmations on locally to exercise the confirmation mail.
- **Consumed by:** `src/pages/api/auth/signin.ts` (writes the choice), `src/pages/api/auth/signout.ts` (clears the marker alongside `active_profile` / `parent_verified`), `src/lib/services/remember-me.ts` (owns the cookie name, the 30-day constant and the read/write/clear helpers), `src/lib/supabase.ts` (`setAll`, and the exported `AUTH_COOKIE_RE` the tests locate the cookie by — never hard-code a project ref).
- **Tests:** `tests/remember-me-cookie.test.ts` (eleven route-level tests against real routes and real local Supabase; the two **refresh** tests are load-bearing, because `getUser()` on a valid token writes no cookie at all and a request-scoped implementation is indistinguishable from a correct one for a full hour; tests 8–11 cover the email-link paths, and 10/11 replay into a *fresh* jar because the jar is keyed by cookie name and would otherwise let `confirm`'s earlier write stand in for `update-password`'s), `tests/signin-form.test.tsx` (the only layer that proves the *rendered* form posts `remember` — drop `name` from the `<Checkbox>` and all seven route tests still pass).
